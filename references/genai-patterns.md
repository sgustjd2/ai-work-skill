# genai-patterns · 생성형 AI 서비스 설계 패턴

fastapi-service, doc-write, deck-write, py-review 가 참조한다. 서비스 유형별 설계와 함정을 담는다. 회사 사실은 여기 없다. 외부 사실의 확인일은 2026-09-23 이고 출처는 `docs/research/sources-2026-09-23.md` 에 있다.

## RAG

문서를 검색해 근거로 답하는 패턴이다. 먼저 RAG 가 필요한지 본다. 지식 전체가 20만 토큰 미만이면 검색 없이 전부 프롬프트에 넣고 프롬프트 캐싱을 켜는 편이 단순하고 정확하다. 최신 상용 모델은 컨텍스트가 100만 토큰이지만 길수록 비용과 지연이 커지니 문서가 자주 바뀌거나 이보다 크면 RAG 로 간다.

1. 수집: 문서를 청크로 나눈다. 청크 크기와 겹침을 정한다(예: 800자, 겹침 100자). 너무 크면 검색이 뭉개지고 너무 작으면 맥락이 끊긴다.
2. 맥락 붙이기: 청크마다 "이 청크가 문서의 어디에서 무엇을 말하는지" 한두 문장을 작은 모델로 만들어 앞에 붙인 뒤 임베딩한다(contextual retrieval). Anthropic 실측에서 이것만으로 검색 실패가 35% 줄었다.
3. 임베딩: 게이트웨이의 `/embeddings` 를 부른다. 모델과 차원을 고정한다. 모델을 바꾸면 벡터 공간이 달라져 전량 재임베딩해야 하니 설정값과 함께 저장한다.
4. 저장: pgvector(0.8.4 이상, HNSW vacuum 손상 수정 포함)에 청크와 임베딩, 문서 출처를 넣는다. 저장 공간이 문제면 `halfvec`, 필터가 붙은 검색은 반복 인덱스 스캔(`hnsw.iterative_scan`)을 켠다.
5. 검색: 벡터와 키워드(BM25)를 함께 돌려 합친다. 정확한 명칭·코드·조문 번호는 순수 벡터 검색이 약하다.
6. 리랭크: 후보 50~150개를 리랭커로 다시 정렬해 상위 20개 안팎을 넘긴다. 임베딩·BM25·리랭크를 모두 쓰면 실패가 67% 줄었다. 오픈 모델은 `bge-reranker-v2-m3`(Apache-2.0, 다국어)가 한국어 기본값이다. `jina-reranker-v3` 는 비상업 라이선스라 쓰지 않는다.
7. 조립: 검색 결과를 프롬프트에 넣고 출처 표기 형식을 지정한다.
8. 검증: 답에 근거 출처가 있는지 확인한다. 근거가 없으면 모른다고 답하게 한다.

질문이 여러 단계 검색을 요구하면(비교, 집계, 후속 질의) 모델이 검색 도구를 반복 호출하는 에이전트형 RAG 를 쓴다. 단계 상한은 아래 에이전트 규칙을 따른다.

## 구조화 출력과 툴 호출

- 응답을 코드로 다뤄야 하면 자유 텍스트 대신 스키마(JSON)를 요구한다. 제공자의 구조화 출력(제약 디코딩, strict 스키마)을 먼저 쓴다. 게이트웨이에서는 `response_format: json_schema` 로 요청한다.
- 제약 디코딩이 있어도 숫자 범위·문자열 길이 같은 제약은 강제되지 않는 경우가 많다. 앱에서 pydantic 으로 다시 검증한다.
- 구조화 출력이 없는 경로가 있다(예: Bedrock 의 Claude). 폴백이 그쪽으로 가면 스키마 검증이 실패할 수 있으므로, 검증 실패 시 오류 메시지를 넣어 한 번 재요청하고 두 번째도 실패하면 사용자에게 오류를 낸다.
- 툴 호출은 도구 목록과 인자 스키마를 명확히 준다. 모델이 부른 인자를 실행 전에 검증한다. 툴 설명은 프롬프트처럼 다듬고, 반환값은 필요한 필드만 짧게 준다.
- 특정 툴을 강제하는 `tool_choice` 를 거부하는 모델이 있다(Claude Opus 5.5 는 400). 기본은 `auto` 와 strict 스키마로 두고, 강제가 필요하면 모델별로 확인한다.
- 툴이 10개를 넘거나 정의가 1만 토큰을 넘으면 전부 싣지 않는다. 자주 쓰는 3~5개만 싣고 나머지는 툴 검색(지연 로딩)으로 찾게 한다. 30~50개를 넘으면 선택 정확도가 떨어진다.

## 에이전트

- 워크플로(정해진 순서의 LLM 호출)로 풀리면 에이전트를 쓰지 않는다. 에이전트는 단계 수를 미리 정할 수 없을 때만 쓴다.
- 단순한 루프에서 시작한다. 단계 수 상한과 비용 상한을 둔다. 무한 루프를 막는다.
- 각 단계의 입력·출력·비용을 로그로 남긴다. 재현할 수 있어야 디버깅이 된다.
- 도구를 늘리기 전에 프롬프트로 풀리는지 본다. 도구가 많을수록 실패 지점이 는다.
- 컨텍스트는 "작고 신호가 높은 토큰"만 넣는다. 긴 작업은 진행 상황을 파일(진행 로그)에 쓰고, 오래된 대화는 요약(compaction)하고, 조사처럼 큰 하위 작업은 서브에이전트에 맡겨 결과만 받는다.
- 작업하는 에이전트와 결과를 평가하는 에이전트를 나눈다. 같은 에이전트가 자기 결과를 채점하면 후하게 준다.
- 자동 실행 범위는 "둘까지 규칙"(Rule of Two)으로 정한다. 신뢰할 수 없는 입력, 민감 데이터 접근, 외부 상태 변경(결제·삭제·발송) 중 셋이 모두 걸리는 행동은 사람이 승인한다.
- 에이전트 사이 통신이 필요하면 A2A(v1.0, Linux Foundation 산하 AAIF)를, 도구 연결은 MCP 를 쓴다. 자체 프로토콜을 만들지 않는다.

## 비동기 작업

- 오래 걸리는 작업은 요청을 막지 않는다. `POST` 는 202 와 작업 id 를 주고, `GET /jobs/{id}` 로 상태를 조회한다.
- 같은 요청을 두 번 받아도 한 번만 실행되게 멱등 키를 받는다.
- 인프로세스 큐는 단일 프로세스에서만 안전하다. 워커가 여럿이면 Redis 큐로 옮긴다.

## 가드레일

- 입력: 길이 제한, 프롬프트 인젝션 패턴 확인. 사용자 입력을 지시 자리에 넣지 않는다. 검색 문서·툴 결과·웹 페이지도 신뢰할 수 없는 입력으로 다룬다(간접 인젝션).
- 출력: 개인정보·시크릿이 새지 않는지 확인한다. 필요하면 마스킹한다. 모델 출력을 SQL·셸·HTML 로 그대로 실행하거나 렌더링하지 않는다.
- 게이트웨이의 guardrails 와 앱의 검증은 역할을 나눈다. 게이트웨이는 공통 정책, 앱은 도메인 규칙.
- 거부·실패를 로그로 남겨 어떤 입력이 막혔는지 추적한다.
- 정책을 바꿀 때는 기존 골든 셋으로 회귀를 확인한다.
- 설계 검토 체크리스트는 OWASP LLM Top 10(2026판)과 에이전트용 OWASP Agentic Top 10(ASI01~ASI10)에 맞춰 항목을 짚는다.
- 국내 서비스는 인공지능기본법(2026-01-22 시행)을 본다. 생성형 AI 를 쓴다는 사실을 이용자에게 미리 알리고, 생성 결과물에 AI 생성 표시를 한다(일반 결과물은 메타데이터·워터마크도 허용, 딥페이크는 눈에 보이는 표시). 고영향 AI 에 해당하면 위험관리·설명·사람 감독·기록 보관 의무가 더 붙는다. 과태료 계도기간은 1년 이상이다. 해당 여부는 법무와 확인한다.

## 평가

- 골든 셋을 만든다. 20~50개의 질문과 기대 답으로 시작한다. 한국어 문항을 반드시 넣는다.
- 검색은 적중률로, 생성은 정답 포함률로 본다. 애매한 품질은 사람이 표본으로 확인한다.
- 채점은 코드(정확 일치·스키마), 모델(LLM 채점), 사람 셋을 섞는다. 에이전트는 매번 결과가 다르니 k 번 중 한 번 성공(pass@k)과 k 번 모두 성공(pass^k)을 구분해 적는다. 운영 품질은 pass^k 가 가깝다.
- 대규모 평가는 외부 도구로 돌린다. promptfoo(2026-03 OpenAI 인수, 오픈소스 유지), DeepEval, Inspect AI 가 있다. 이 저장소는 골든 파일·계약 테스트까지만 다룬다.

## 비용과 지연

- 모델을 등급으로 나눈다. 쉬운 작업은 작은 모델, 어려운 작업만 큰 모델. 게이트웨이에서 등급을 별칭(`chat`, `chat-fast` 등)으로 두면 모델을 바꿔도 앱을 고치지 않는다.
- 추론 모델은 노력 수준(effort, reasoning effort)으로 비용과 지연을 조절한다. 기본값을 그대로 두지 말고 작업별로 골든 셋에서 낮은 값부터 올려 본다.
- 같은 입력이 반복되면 캐시한다. 제공자 프롬프트 캐싱은 앞부분이 같아야 적중하므로 시스템 프롬프트·툴 목록·고정 문서를 앞에, 바뀌는 입력을 뒤에 두고 툴 순서를 고정한다. 캐시 적중 입력은 정가의 5~10% 수준이다. 응답 캐시가 필요하면 게이트웨이 캐시를 켠다.
- 급하지 않은 대량 작업(일괄 요약·임베딩 재생성)은 배치 API 로 돌린다. 보통 절반 가격이다.
- 사용자 체감이 중요하면 스트리밍을 먼저 고려한다. 첫 토큰까지의 시간을 줄인다.
- 토크나이저가 바뀌면 같은 글도 토큰 수가 달라진다(최신 Claude 는 약 30% 증가). 모델을 바꿀 때 단가만 보지 말고 같은 입력으로 실제 비용을 잰다.

## 설계서에 넣을 구성도

RAG 서비스의 목표 구성은 다음 형태다. 설계서에서는 ` ```diagram ` 블록으로 그린다.

```diagram
type: architecture
direction: LR
groups:
  - { id: app, label: 서비스, style: highlight }
nodes:
  - { id: api, label: RAG API, kind: service, group: app }
  - { id: gw, label: LiteLLM, kind: gateway, group: app }
  - { id: pg, label: pgvector, kind: data, group: app }
  - { id: rr, label: 리랭커, kind: llm, group: app }
edges:
  - { from: api, to: gw, label: 임베딩·생성 }
  - { from: api, to: pg, label: 벡터·키워드 검색 }
  - { from: api, to: rr, label: 리랭크 }
```
