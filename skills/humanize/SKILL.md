# humanize

AI 티를 지우는 스킬이 아니다. 글에 빠진 것(문체·재료·판단)을 찾아 사용자의 것으로 채우는 스킬이다. 표면 신호(em-dash·상투어·이모지·3항목·요약 문단)는 `doc_lint` 훅이 이미 막는다. 이 스킬은 정규식이 못 잡는 것, 즉 재료 없는 일반론, 근거 없는 사실, 판단 없는 나열을 맡는다. 원본 개념은 위키독스 "누구나 할 수 있는 AI 글쓰기" 02장이고 요약은 PRD 부록 G 에 있다.

핵심 질문은 하나다. "이 문장을 다른 사람이 써도 그대로 말이 되는가." 그대로 말이 되면 아직 사용자의 재료가 덜 들어간 것이다.

## 모드

인수가 없으면 대상 파일이 있을 때 `진단`, 없을 때 `사전` 이다.

| 모드 | 언제 | 나오는 것 |
|---|---|---|
| `사전` | 산출물을 만들기 전 | 핵심 3줄과 재료 표. 담당 스킬(doc-write 등)로 넘긴다 |
| `진단` | 초안이 있을 때(AI 가 썼든 사람이 썼든) | 3축 진단 보고와 확인 후보 표. 파일은 고치지 않는다 |
| `재작성` | 진단 뒤 사용자가 재료를 줬을 때 | 부족한 축만 채운 파일 |

## 사전 (산출물 전)

1. 핵심 3줄을 사용자의 말로 받아 적는다. 사용자가 이미 말했으면 되묻지 않는다.
   - 주장: 말하고 싶은 것 한 문장
   - 근거: 그렇게 생각하는 이유나 실제 재료(수치·경험·자료·결정)
   - 미확인: 아직 확인하지 못한 부분, 또는 사용자가 직접 남길 판단
2. 재료 표를 채운다. 열은 `재료 | 출처 | 어느 절에 쓰나` 다. 재료가 없는 절이 보이면 질문을 최대 3개 한다. 답이 없어도 멈추지 않는다. 그 자리는 `[확인 필요]` 로 두고 진행한다.
3. 담당 스킬로 넘긴다. 문서는 `doc-write`, 덱은 `deck-write`, 브리프는 `ai-trend-brief`, 리뷰는 `py-review`. 담당 스킬의 리드 선언(유형·독자·톤)은 그대로 한다. 핵심 3줄은 내용이고 리드는 형식이다.
4. 핵심 3줄을 산출물 파일 맨 위에 HTML 주석으로 남긴다. `진단` 때 원본성 대조에 쓴다. 렌더러와 doc_lint 는 주석을 무시한다.
   ```
   <!-- humanize: 주장 … / 근거 … / 미확인 … -->
   ```

## 진단 (초안 후)

1. 스크립트를 돌려 기계가 잡는 것을 먼저 받는다.
   ```bash
   python "${CLAUDE_PLUGIN_ROOT}/skills/humanize/scripts/humanize_scan.py" docs/arch/<파일>.doc.md
   ```
   클론 상태면 `python skills/humanize/scripts/humanize_scan.py <파일>` 이다. `--json` 을 붙이면 구조화 출력이다. 종료코드는 항상 0 이다. 결과는 판단 재료이지 판정이 아니다.
2. `references/three-axes.md` 를 읽고 축별 질문을 초안에 던진다. 문장마다 "다른 사람이 써도 그대로 말이 되는가" 를 묻고, 그런 문장에 어느 축이 빠졌는지 적는다.
3. `references/verify-table.md` 형식으로 확인 후보 표를 채운다. 스크립트가 뽑은 후보에 눈으로 찾은 것을 더한다. 근거 열은 사용자 자료, URL, `[확인 필요]` 셋 중 하나만 쓴다. 근거를 지어내지 않는다.
4. 파일 상단에 핵심 3줄 주석이 있으면 원본성을 대조한다. 주장이 빠졌는지, 다른 뜻으로 바뀌었는지, 미확인 항목이 확정문으로 둔갑했는지 본다.
5. 보고한다. 형식은 고정이다.

```
## 사람화 진단: <파일>
부족한 축: <문체 | 재료 | 판단> (복수 가능) · 재료 밀도 <n.nn>
### 근거 문장
- [줄] <문장> → <어느 축, 왜>
### 다음에 넣을 입력
- <사용자에게 요청할 재료 1~3개>
### 지금 고칠 것 1개
- <가장 효과 큰 수정 하나>
### 확인 후보 (n건, 근거 없음 m건)
| 줄 | 문장 | 종류 | 근거 | 상태 |
```

진단 모드에서는 파일을 고치지 않는다. 사용자가 재료를 주거나 "고쳐줘" 라고 하면 `재작성` 으로 간다.

## 재작성 (재료를 받은 뒤)

1. 진단의 "부족한 축" 만 손댄다. 멀쩡한 절을 다시 쓰지 않는다.
   - 문체: `STYLE.md` 의 톤(`tone_doc`·`tone_deck`)과 `doc-write/references/writing-rules-ko.md` 를 따른다. 문단 길이를 일부러 다르게 둔다. 판단 문장에는 주어를 둔다.
   - 재료: 사용자가 준 재료를 문장 단위로 넣는다. 넣을 재료가 없는 자리는 지우거나 `[확인 필요]` 로 둔다. 없는 경험·수치·출처를 만들지 않는다.
   - 판단: 선택하지 않은 대안이 왜 밀렸는지, 단점과 하지 않을 것, 다음 행동(누가·언제·무엇을)을 쓴다. 교훈형 마무리는 다음 행동으로 바꾼다.
2. 다 쓰면 `진단` 을 한 번 더 돌려 확인 후보의 "근거 없음" 건수가 줄었는지, 핵심 3줄이 보존됐는지 본다. 세 번째 패스는 없다.
3. 파일은 Edit/Write 도구로 쓴다. Bash 리다이렉트로 쓰면 훅을 우회하므로 하지 않는다.

## 다른 스킬과의 관계

- `doc-write`·`deck-write` 는 리드 선언 앞에서 `사전` 을, 종료 점검에서 `진단` 의 3축 질문을 쓴다.
- 짧은 산출물(메일·회의록·리뷰 코멘트)은 재료와 톤만 본다. 설계서·검토보고서·제안서는 판단까지 본다. 글의 무게에 맞춰 축을 하나씩 넣는다.
- 표면 신호가 남아 있으면 이 스킬이 아니라 `doc_lint --all <파일>` 을 먼저 돌린다.

## references

- `three-axes.md`: 축별 진단 질문, 신호 6개와 사람 글의 대비, 부족한 축을 정하는 기준, 원본성 대조.
- `verify-table.md`: 확인 후보의 종류 5가지, 표 형식, 근거 열 채우는 규칙, 환각이 잘 생기는 요청.

## 하지 않는 것

- AI 탐지기를 피하려고 문체를 흉내내기. 목적은 위장이 아니라 사용자의 목소리·근거·판단을 되돌리는 것이다.
- 재료 없이 표면 신호만 지우고 "사람화 완료" 라고 하기.
- 사용자가 주지 않은 경험·수치·출처·인용을 만들어 넣기.
- 진단 모드에서 파일 수정.
- 담당 스킬의 골격·톤·렌더링 규칙을 덮어쓰기.
