# deck-method · 덱 제작 순서와 수정 기준

덱을 한 번에 다 만들지 않는다. 내용을 먼저 정리하고, 디자인 기준을 정하고, 본문 두 장으로 기준을 맞춘 뒤 전체로 넓힌다. 원천은 `docs/research/sources-2026-09-24.md` 의 영상이다. 색·폰트·금지 항목은 여전히 테마와 `slide-rules.md` 가 원본이다.

## 1. 내용부터 정리한다

줄글 상태의 원고를 바로 장표로 만들지 않는다. 정리하는 동안 무엇을 강조하고 어떻게 구조화할지 기준이 생기고, 그 기준이 있어야 결과물에 구체적으로 피드백할 수 있다.

- 슬라이드마다 핵심 문장 한 줄. 성과를 나열하지 않고 한 단계 큰 의미를 담는다. 이것이 헤드 메시지(`##`)가 된다.
- 슬라이드 유형별로 파트를 정한다. 예: 플랫폼 성과 장은 집계 기간·도달·주요 성과·특이 사항, 사례 장은 이미지 자리·성과·성공 요인.
- 어투를 하나로 맞춘다. 명사형과 서술형이 섞이면 명사형으로 통일한다.
- 설명이 긴 문장과 반복은 지운다. 단, 원문의 수치·사실을 바꾸거나 지우는 것은 사용자 판단이다. 제안으로만 남긴다.
- 원본(`.doc.md`, 사용자 원고)은 따로 두고 `.deck.md` 에서만 작업한다. 디자인 중에 내용이 바뀌면 원본과 대조해 되돌린다.

## 2. 디자인 기준 네 가지를 먼저 정한다

"깔끔하게, 세련되게" 는 기준이 아니다. 아래 넷을 값으로 정한 뒤 쓴다.

| 기준 | 정하는 곳 | 비고 |
|---|---|---|
| 비율 | 테마 `pptx` 치수 | 발표 16:9 기본. 서면 제출이면 A4 로 쓸지 한 줄로 확인 |
| 색 | 테마 json | 배경·메인·보조·본문 텍스트 네 가지를 hex 로. 이름("파란색")으로 말하지 않는다 |
| 폰트 | 테마 json | 제목용·본문용 두 가지. 본문은 중요도에 따라 굵기로 위계 |
| 레퍼런스 | 사용자 자료 | 3~5장, `레퍼런스1`, `레퍼런스2` 처럼 번호로 부른다 |

- 회사 테마·`template_pptx` 가 있으면 색·폰트는 거기서 끝난다. 새로 고르지 않는다.
- 회사 테마가 없고 사용자가 레퍼런스나 기존 pptx 를 주면 `theme_from_pptx` 로 색·폰트를 뽑아 테마 json 에 넣는다. 렌더러 소스에 hex 를 쓰지 않는다.
- 레퍼런스는 이미지만 받지 않는다. "레퍼런스2 의 수치 강조 방식", "레퍼런스1 의 여백" 처럼 가져올 요소를 번호와 함께 한 줄씩 적게 한다. 말로 설명하기 애매한 구조는 레퍼런스 한 장이 가장 정확하다.

## 3. 본문 두 장으로 기준을 맞춘다

1. 스토리라인 확인 뒤 표지를 뺀 본문 중 구조가 다른 두 장만 `.deck.md` 에 완성해서 쓴다.
2. 렌더링하고 `preview` 로 그 두 장만 본다.
3. 공통 요소를 고정한다: 제목은 작게, 헤드 메시지 위치·크기, 좌우·상하 여백, 본문이 들어갈 영역. 모든 장에서 같은 자리에 온다.
4. 수정은 두세 번 돌린다. 매 수정 요청에 레퍼런스 번호와 처음 정한 기준을 다시 붙인다. 수정 사항만 주면 기준에서 벗어난다(영상에서 도형에 없던 선이 생긴 사례).
5. 두 장이 합의되면 그 두 장을 기준 슬라이드로 선언하고 나머지를 같은 서식으로 쓴다.

첫 결과가 마음에 들지 않는 것이 정상이다. 전체를 먼저 만들면 틀린 기준이 모든 장에 복제되고 토큰도 많이 든다.

## 4. 프롬프트 방식과 템플릿 방식

| 상황 | 방식 |
|---|---|
| 디자인 방향이 아직 없음, 매 장 구조가 다름 | 테마 + 이 문서 3절의 두 장 파일럿 |
| 스타일이 정해져 있고 같은 구조가 반복됨(주간·월간 리포트, 카탈로그) | `template_pptx`. 목차별 레이아웃을 슬라이드 마스터에 두고, 섹션 이름을 목차와 맞춘다. 파일럿 없이 바로 전체 |

템플릿 방식은 설명이 짧아지는 대신 레이아웃을 먼저 만들어야 한다. 한 번 합의된 파일럿 결과는 회사 템플릿 후보로 `STYLE.md` 에 기록한다.

## 5. 수정 기준: 이 장의 메시지가 전달되는가

체크리스트보다 판단 기준 두 개를 먼저 본다.

- 강조해야 할 것이 강조되어 있는가. 트렌드 이름보다 그 의미를 설명하는 한 줄이 더 커야 한다. 헤드 메시지 핵심 구절은 굵게.
- 근거 데이터가 한눈에 들어오는가. 숫자만 나열되어 있으면 ` ```chart ` 로 바꾼다. 전월 대비처럼 두 값과 증감률이면 막대 두 개와 증감 표시.

그다음 AI 가 만든 장표에서 자주 보이는 흔적을 지운다.

| 흔적 | 조치 |
|---|---|
| 정렬이 어긋남, 칸 너비가 제각각 | 같은 폭 칸으로 나누고 요소를 칸 중앙에 |
| 공간이 남는데 글자가 작음, 아래 여백 과다 | 본문 크기를 키워 영역을 채운다 |
| 제목·헤드 메시지가 장의 절반을 차지 | 제목은 줄이고 본문 영역을 넓힌다 |
| 같은 급의 항목 중 하나만 다른 색 | 같은 서식으로 맞춘다. 강조는 결론 한 곳 |
| 자간을 넓힌 텍스트 | 기본 자간 또는 좁게 |
| 단어 중간 줄바꿈 | 줄을 다시 끊거나 문장을 줄인다 |
| 쪽 번호 없음 | 바닥글 쪽 번호 유지(docgen 기본) |
| 장식용 아이콘 | 뺀다(`slide-rules.md`) |

## 6. 누가 고치나

- 구조 변경(배치 축, 차트 종류, 파트 재구성): `.deck.md` 를 고쳐 다시 렌더링한다.
- 몇 mm 정렬, 줄 간격, 표지 이미지 위치: 사용자가 PowerPoint 에서 직접 고치는 편이 빠르다. 이 차이를 사용자에게 한 줄로 알린다.
- AI 가 만든 이미지는 품질 편차가 크다. 표지 비주얼은 사용자가 준비한 것을 쓴다.

## 가져오지 않은 것

영상에는 있지만 이 조직 덱 규칙과 맞지 않아 쓰지 않는다: 배경 그라데이션, 아이콘 생성·삽입, 애니메이션과 HTML 발표 자료, AI 표지 이미지, 폰트 파일 업로드(폰트는 테마가 정한다), 웹 Claude 스킬 만들기(이 플러그인의 `deck-write` 가 그 역할이다).
