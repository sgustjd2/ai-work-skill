# deck-write

발표용 덱을 쓴다. 색·폰트·회사 사실은 `STYLE.md` 와 테마가 원본이다. 여기에 복사하지 않는다. 덱은 Edit/Write 도구로 쓴다. Bash 리다이렉트로 쓰면 훅을 우회하므로 하지 않는다.

## 절차

1. 읽는다. `STYLE.md` 를 읽는다(없으면 `/ai-init` 을 안내하고 멈춘다). 테마 이름과 `template_pptx`(회사 템플릿)를 확인한다. 회사 템플릿이 있으면 레이아웃 이름을 `python -m docgen layouts <파일>` 로 본다. 입력이 `.doc.md` 이면 그 문서의 개요, 비교표, 구성도, 권고안을 스토리라인의 재료로 뽑는다. 내용을 새로 만들지 않는다.

2. 덱 리드를 한 줄로 선언한다.
   `덱: <제목> · 목적 <보고|제안|공유|교육> · 독자 <경영진|개발팀|고객> · 장수 <n> · 결론 <한 문장>`
   결론 문장이 덱의 마지막 슬라이드 헤드 메시지가 된다.

3. 스토리라인을 먼저 보인다. 슬라이드 제목(`#`)과 헤드 메시지(`##`)만 n장 나열해 사용자에게 한 번 확인한다. 흐름은 배경·문제, 목표, 대안·아키텍처, 비교·근거, 계획·일정, 위험, 결론·요청 순서다. 교육용은 목표, 개념, 실습 단계, 정리 순서다.

4. 쓰기 직전에 `references/slide-rules.md` 를 읽는다. 아키텍처 덱이면 `../doc-write/references/arch-doc-types.md` 의 구성도 규약도 따른다. 핵심 규칙은 다음과 같다.
   - 헤드 메시지는 주장 문장이다. 60자 안. "게이트웨이 선정"이 아니라 "LiteLLM 이 운영 부담 대비 기능이 가장 넓다".
   - 본문은 여섯 줄 이하, 줄당 40자 이하, 명사형으로 끝낸다.
   - 슬라이드마다 그림 하나 또는 표 하나. 같은 크기 카드 세 개를 나열하지 않는다.
   - 아이콘·이모지는 쓰지 않는다. 애니메이션·화면 전환은 없다.
   - 출처는 바닥글에 둔다. 첫 장에 결론 요약, 마지막 장에 요청 사항(결정·예산·일정)을 둔다.

5. 레이아웃을 고른다. `references/layouts.md` 의 열 가지 기준을 따른다. 구성도는 ` ```diagram `, 일정은 ` ```timeline `, 수치 비교(비용·처리량·사용량)는 ` ```chart `, 정성 비교는 표로 쓴다. 차트 하나에 시리즈는 넷 이하, 값에는 단위와 출처를 붙인다.

6. 파일은 `docs/deck/<제목>.deck.md` 로 쓴다. frontmatter 를 채운다(제목·부제·조직·작성자·일자·테마·바닥글, 목차가 필요하면 `agenda: true`). 렌더링은 다음으로 한다.
   ```
   python -m docgen render-pptx docs/deck/<제목>.deck.md --out docs/_build/<제목>.pptx
   ```
   회사 템플릿을 쓰면 `--template <회사.pptx>` 를 붙이거나 `STYLE.md` 의 `template_pptx` 를 채운다. `preview` 가 되면 전 장 썸네일을 한 번 보고 넘침·겹침만 확인한다. 렌더 오류는 DSL 위반이므로 `.deck.md` 를 고친다. python-pptx 를 직접 부르지 않는다. 훅이 막는다.

7. 점검한다. `references/slide-rules.md` 의 체크 여덟 개를 한 번 돌리고 끝낸다. 경영진 덱은 슬라이드마다 발표자 노트(`<!-- note: -->`)에 말할 내용을 두세 문장 넣는다.

## 브리프가 이긴다

사용자가 특정 구조·색·장수를 명시하면 그것이 우선한다. 하드 룰에 걸리면 먼저 한 줄로 확인한다. 승인되면 파일에 마커를 남기고 `STYLE.md` 6절에 기록한다.

## 하지 않는 것

- 글머리표만 가득한 슬라이드, 제목만 있는 슬라이드.
- "감사합니다" 만 있는 마무리 장. 마무리 장은 요청 사항과 연락처를 둔다.
- 그라데이션·그림자·클립아트.
- python-pptx 직접 호출, Bash 리다이렉트로 덱 작성.
- 내용을 지어내기. 원본 문서나 사용자 자료에 없는 수치·회사명은 쓰지 않는다.
