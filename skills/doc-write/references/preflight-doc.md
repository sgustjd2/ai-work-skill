# 종료 전 점검

문서를 다 쓴 뒤 한 번 돌린다. 발견한 것을 한 번에 고치고 끝낸다. 세 번째 패스는 없다. 정규식으로 잡히는 것은 doc_lint 이 이미 본다. 이 목록은 사람(모델)이 눈으로 보는 것이다.

## 공통 점검

- 결론(권고안)이 문서 첫 화면 안에 있는가. 개요 3~5줄만 읽어도 맥락이 잡히는가.
- 사실·추론·권고가 표현으로 구분되는가(`~이다` / `~로 예상된다` / `~하는 것이 적절하다`).
- 선택하지 않은 대안이 왜 밀렸는지 한 줄이라도 있는가. 장점만 나열하지 않았는가.
- 모든 수치·모델명·금액·일정이 입력 자료와 같은가. 지어낸 숫자는 없는가.
- 문단 길이가 제각각인가. 모든 문단이 세 문장이면 기계 티가 난다.
- 마지막 문단이 앞 내용을 반복하지 않는가. 다음 행동(누가·언제·무엇을)으로 끝나는가.
- 표의 마지막 열이 "검토 의견"(판단)인가. 값 나열로 끝나지 않았는가.
- `[확인 필요]` 항목이 "추가 확인사항" 절에 모여 있는가.
- 회사 색과 폰트만 썼는가(렌더링 결과는 렌더링 단계에서 확인).

## 유형별 추가 점검

- 설계서: TO-BE 구성도가 3수준(맥락·컨테이너·핵심 흐름)인가. AS-IS 의 한계가 TO-BE 의 근거로 이어지는가. 인터페이스 표가 라우트 표와 일치하는가.
- 검토보고서: 비교표가 실제 의사결정 항목을 비교하는가. 임의 점수화가 없는가. 종합 의견이 값 요약이 아니라 판단인가.
- 가이드: 명령 블록이 그대로 실행되는가. 준비물과 확인 방법이 있는가. 존댓말이 일관되는가.
- 런북: 증상마다 확인·조치·에스컬레이션이 있는가. 연락처가 최신인가.
- 브리프: 항목마다 URL 과 날짜가 있는가. 적용 아이디어에 대상 서비스가 적혀 있는가.

## 브리프가 이길 때

사용자가 특정 표현·구조를 명시했으면 그 지시가 규칙보다 우선한다. 하드 룰에 걸리면 먼저 한 줄로 확인하고, 승인받은 예외만 마커와 `STYLE.md` 6절 기록으로 남긴다.
